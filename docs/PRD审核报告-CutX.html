这份文档的质量在命令行工具类 PRD 里属于上乘——命令格式、参数说明、异常处理表、退出码规范、 清单文件格式都写得具体且可执行。问题不在"写了多少",而在几个关键维度"写了但不够厚":没有显式列出"不做什么"， 验收标准散落在处理逻辑里而缺少正式的"给定条件→操作→预期结果"写法，风险有识别但没指定负责人和应对策略。 这些都不是从零补起，而是把已有内容收紧一档。补齐后可以到"可交付开发"。

审核总结

这份 PRD 明显是一个有工程思维的人写的。它做对了三件难做的事：一是把命令行接口写得非常具体——每个子命令的 参数、默认值、校验规则都有表格，工程师拿到就能直接写 argparse/cobra；二是异常处理表覆盖了大量真实场景（源文件 不存在、磁盘空间不足、分片校验失败、中途中断），而且每条都给了明确的退出码，这是很多 PRD 会漏的地方；三是技术 方案选型有理有据——选 Go 因为静态编译单一二进制、选 SHA-256 因为安全性高，不是拍脑袋。

完成度落在 68% 而不是更高，原因是几个"必填且阻断"的维度只到了"部分"而非"完整"。具体来说：文档没有一段显式的 "非目标"声明（只在迭代规划里暗示了 V2.0 才做压缩和加密，但没有明确说"本期不做"）；验收标准虽然通过处理逻辑和异常 表实际上覆盖了不少场景，但没有一条用"给定……当……则……"的格式写出来，工程师对"什么算做完了"没有可逐条勾选的 判据；风险清单列了四条技术风险但没有负责人、没有概率和影响的评估。这些每一条单独看都不算致命，但合在一起意味着 开发过程中还会遇到几个需要现场拍板的模糊地带。

裁决给"有条件交付"而不是"暂不可交付"，是因为没有任何阻断维度是完全缺失的——它们都有内容，只是不够厚。开发可以 先从骨架代码（命令行框架 + 流式切割 + 流式合并的核心逻辑）起步，同时收紧下面列出的几个条件。

必须补齐（阻断项）

以下每条对应的维度目前为"部分"而非"完整"。它们不阻止开发从骨架起步，但在 MVP 完成前必须收紧，否则会在开发中途产生需要现场拍板的模糊地带。

必须补 验收标准要写成可逐条勾选的判据 对应:§5 详细功能说明

现在的处理逻辑是散文式的"1.解析参数 2.获取大小 3.流式读取..."，工程师能看懂大致流程，但缺少能逐条 打勾的验收判据。比如"切割完成"的判据是什么——50个分片每个恰好2GB？最后一个可以是剩余大小？清单文件必须是合法 JSON且包含所有必填字段？这些没有写成可测的断言。

怎么补
  • 为每个子命令的核心场景补 3~5 条验收标准，用"给定……当……则……"的格式。例：给定一个100GB文件和2GB切割大小，当执行 split 完成，则生成50个分片，前49个各2147483648字节，最后一个为剩余大小，清单文件为合法JSON且包含全部字段。
  • 异常场景已有的处理表可以直接改写成验收标准格式，它们内容已经到位，只差格式转换。
  • 把"切割成功的判据"显式写出来：分片数量、每个分片大小规则、清单文件字段完整性。

必须补 补全边界场景的已决定行为 对应:§5.1.1 异常处理 + §9 质量检查

异常处理表覆盖了文件不存在、磁盘不足、校验失败、中断等常见场景，这是亮点。但有几个边界场景只在第9节 测试要点里提了一嘴，没有在功能说明里写明行为。

怎么补
  • 999分片上限：§5.1.1 只在命名规则里提了"最多999个分片"，但超过时怎么处理没写——是报错退出还是自动切换到4位序号？需要明确。
  • 文件名含特殊字符/空格/中文：分片命名用"{原始文件名}.part001"，如果文件名含路径分隔符或特殊字符怎么办？需在命名规则里说明处理方式（如仅取文件名部分、不含目录）。
  • Windows路径含空格：示例命令 cutx split big file.img 在Windows上可能被截断，需在帮助文档里提示引号用法。
  • 源文件是符号链接：跟随链接读源文件还是拒绝？需决定。

必须补 显式列出非目标 对应:§2 项目背景 / §8 迭代规划

文档在迭代规划里暗示了 V2.0 才做压缩、加密、TUI，但没有一段显式声明"本期不做"。对一个工具型产品来说， 范围蔓延的风险在于"顺便也加上目录遍历""顺便也做增量同步"——非目标声明能挡住这些。

怎么补
  • 在§2 加一段"非目标"：V1.0 不做文件压缩（分片为原始字节拷贝）、不做加密、不做目录递归（仅处理单文件）、不做增量同步、不做图形界面。
  • 把"分片文件是原始数据的直接切分，不压缩不加密"作为设计原则写明，这关系到客户是否理解分片和原文件的总大小一致。

必须补 风险要指定负责人和应对策略 对应:§9 质量检查报告

§9 列了四条技术风险（100GB耗时、SHA-256慢、FAT32限制、Windows换行符），但格式是"问题→建议"而非 "风险→概率×影响→触发条件→负责人→应对策略"。对FAT32这种已知会导致数据损坏的风险，没有负责人跟踪是不够的。

怎么补
  • 把四条风险改成正式格式，每条标注概率（高/中/低）、影响（高/中/低）、触发条件、负责人、应对策略。
  • FAT32风险建议标为"概率中×影响高"，应对策略：切割前检测目标分区文件系统类型，如果是FAT32且分片大小≥4GB则输出警告并中止。
  • 补一条"用户误操作（如分片和清单不在同一目录）"的风险，这在离线U盘传输场景下很常见。

建议完善

建议补 补一个产品级成功指标 对应:§2.1 / §6

文档有技术性能指标（速度、内存、体积），但没有一个回答"这个工具成功了意味着什么"的指标。 对文件完整性工具来说，最自然的成功指标是"零数据损坏"。

怎么补
  • 加一个核心指标：切割→传输→合并全链路数据完整性——合并后文件的SHA-256与原始文件一致，校验失败率 = 0。
  • 加一个底线指标：分片校验失败时必须中止合并（不允许跳过损坏分片继续合并），这已经在设计中但应显式写为指标。

建议补 补工作量估算和依赖梳理 对应:§8 迭代规划

V1.0/V1.1/V2.0 的功能切分清楚，但没有任何工作量估算。即使是新项目，也应该给出相对大小或区间。

怎么补
  • 用 T 恤尺寸（XS~XL）标注 V1.0 各模块：split 核心逻辑（M）、merge 核心逻辑（M）、verify（S）、CLI框架（S）、进度条（S）、交叉编译脚本（XS）。
  • 列出依赖：Go 1.21+ 工具链、Cobra 库（可 vendored 离线编译）、5个目标平台的交叉编译环境。
  • 给一个区间而不是精确日期：如"预计2~3周，取决于是否需要断点续切"。

建议补 补正式用户故事 对应:§3.2 / §5

用户画像和角色定义有了（交付工程师、客户运维、系统管理员），功能描述也隐含了用户视角，但没有 "作为……我希望……以便……"格式的用户故事，会让需求评审时缺少"从用户价值出发"的锚点。

怎么补
  • 为3个核心命令各写1~2条用户故事。例：作为交付工程师，我希望指定切割大小就能把100GB文件切成2GB分片，以便逐个上传到有大小限制的客户服务器。
  • 用户故事不替代详细功能说明，只是给每个功能一个"为什么存在"的锚。

可优化 清单文件的 nullability 语义细化 对应:§5.2.1

清单文件格式写得很好，字段类型和说明都有。唯一可以再细的是 overall_hash 的 null 语义—— 当前写的是"--no-overall-hash 时为 null"，但如果用户没加这个参数但计算失败了呢？

怎么补
  • 明确 overall_hash 的三种状态：有值（计算成功）、null（用户用 --no-overall-hash 跳过）、缺失该字段（兼容旧版本清单）。合并时对 null/缺失的处理分别是"跳过整体校验"和"跳过并输出提示"。
  • 考虑 manifest_version 的前向兼容策略：旧版本工具读到高版本清单时怎么处理（报错退出？尝试读取兼容字段？）。

可优化 补发布前检查清单 对应:§4 核心业务流程

verify-then-merge 的工作流已经隐含了上线验证，但没有一个显式的"交付前检查清单"。

怎么补
  • 在§4 补一个检查清单：切割后自校验（split 完成后自动 verify 一次）、传输后校验（客户环境 verify）、合并后整体校验。
  • 考虑在 split 完成时自动输出一条"合并命令"提示（如"This file can be restored with: cutx merge xxx.manifest.json"），降低客户运维人员的使用门槛。

逐节点评

§2 项目背景 ✅ 完整

问题陈述清晰：谁（交付工程师）、为什么痛（客户服务器有文件大小限制、环境离线）、后果（无法传输大文件）。 用户画像分了三类（交付工程师、客户运维、系统管理员），各自的诉求区分度高。
  • 可以补一句量化现状：当前一次100GB文件交付要多久（手动split+无校验+逐个上传），有了对比，工具的价值更具体。

§4 核心业务流程 ✅ 完整

Mermaid 流程图清晰覆盖了"切割→传输→校验→合并→整体校验"全链路，包括校验失败回到重传的分支。 两个典型使用场景的命令示例很实用，直接能照着跑。
  • 场景1的"51个文件"说法建议改成"50个分片 + 1个清单文件"，避免歧义。

§5.1 文件切割 ⚠️ 部分

命令格式、参数表、处理逻辑、进度格式、异常处理表都写得很到位——参数的默认值、校验规则、退出码一应俱全。 差距是验收标准没写成可逐条勾选的格式（见"必须补"第一条），以及几个边界场景行为缺失（见"必须补"第二条）。
  • 进度显示格式的 ETA 计算方法建议说明：是基于已用时间推算还是固定速率假设？

§5.2 清单文件 ✅ 完整

JSON 结构清晰，字段类型表完整，示例真实。这是这份 PRD 最扎实的部分之一——它就是 split 和 merge 之间的数据契约， 写得好就能保证两端独立开发不出错。
  • 唯一可细化的是 overall_hash 的 null 语义（见"可优化"第一条）。

§5.3 文件合并 ⚠️ 部分

处理逻辑分四阶段（预检→校验→合并→后校验），逻辑严谨。异常表覆盖了清单缺失、分片缺失、大小不匹配、校验失败、 磁盘不足、中断等场景。
  • 合并阶段的进度计算方式没说明——是按分片数还是按字节数？对最后一个分片（可能只有几百MB）的进度跳变要有处理。
  • --skip-verify 参数建议加一个确认提示（"跳过校验可能导致数据损坏，确定继续？(y/N)"），防止误操作。

§5.4 完整性校验 ✅ 完整

作为一个独立子命令设计得合理——传输后先验证再合并，符合实际交付流程。命令和输出格式清晰。
  • 建议补一条：verify 也检查清单文件自身的完整性（如 JSON 格式是否合法、必填字段是否齐全）。

§6 非功能需求 ✅ 完整

性能、安全、兼容性、离线要求全部写成可测的数字或可勾选的条目。这是很多 PRD 最敷衍的一节，这份做到了认真对待。
  • SHA-256 计算速度"≥300MB/s（单核）"建议注明是在什么硬件基准上（如 Apple M2 / Intel i7-12700），否则不同环境下不可比。
  • 兼容性表里提到"FAT32单文件4GB限制"，但切割分片默认2GB，恰好不触发——不过用户如果设4G就会触发，建议在帮助文档里加提示。

§7 技术方案 ✅ 完整

选型有理有据（Go→静态编译、Cobra→CLI成熟、SHA-256→安全+硬件加速），交叉编译目标表覆盖了5个平台， 核心算法用伪代码展示了流式切割和合并的逻辑。
  • 伪代码里合并算法的"边写边校验"策略值得肯定——不是先全部校验完再合并，而是在写入的同时计算hash，校验失败时已写入部分需处理（是删除输出文件还是保留？建议明确）。

§8 迭代规划 ⚠️ 部分

V1.0/V1.1/V2.0 三段切分清晰，MVP 范围合理（核心功能+校验+进度，不含断点续传和高级功能）。 但无工作量估算、无依赖梳理（见"建议补"第二条）。
  • V1.1 的"断点续切"和"断点续合并"对100GB级别文件是刚需——如果一次切割要12分钟，中断后重来很痛。建议评估是否提到 V1.0。

§9 质量检查报告 ⚠️ 部分

四角色审查（技术/用户/运营/测试）的思路对，内容也有料——FAT32限制、Windows换行符、空文件切割等都是真实问题。 但风险格式不够正式（见"必须补"第四条），测试要点的预期结果可以更具体。
  • 测试要点第8条"999个分片上限"只写了"超过时输出错误提示"，但没说超过后是否允许继续（如自动切4位序号还是硬中止）。

做得好的部分

  • 命令行接口设计专业。每个子命令有参数表（含类型、默认值、校验规则），分片命名规则有定义，退出码有四档规范（0/1/2/130）。拿到这份文档，工程师可以直接开始写 CLI 框架和参数解析，不需要猜测。
  • 异常处理表是整份文档的亮点。每个子命令都有独立的异常处理表，覆盖了文件不存在、磁盘不足、校验失败、中断等真实场景，每条都有触发条件和处理方式+退出码。很多 PRD 在这一节只写"妥善处理异常"，这份做到了逐条决定行为。
  • 清单文件格式作为数据契约写得扎实。JSON 结构 + 字段类型表 + 示例 + 版本号，它让 split 和 merge 可以独立开发、独立测试，是工程上最关键的一份契约。
  • 非功能需求全部落成数字。内存≤50MB、速度≥500MB/s、二进制≤10MB——不是"要快""要轻量"，是可测的。
  • 技术选型有理有据。选 Go 不是因为流行，是因为静态编译单一二进制+交叉编译原生支持，直接对齐了"离线+跨平台"的核心约束。
