# 默认 quick 模式：速度优先，校验可选

CutX 的 merge 命令默认使用 `--mode quick`（纯 I/O 合并，不校验），而非默认校验。用户通过 `--mode verify` 显式启用边写边校验。split 阶段始终在单遍流式读取中计算 hash（零额外 I/O），保证清单中始终有 hash 值，用户事后随时可用 `cutx verify` 补校验。

**为什么默认不校验**：CutX 是一个大文件交付工具，核心场景是"快速切割、快速合并"。100GB 文件 quick 合并约 5 分钟，verify 合并约 6 分钟——差距虽不大，但工具的定位是"简单、快"，默认校验与此定位不符。校验的增量价值是"在合并时发现传输损坏"，但用户可以在合并前用 `cutx verify` 独立校验，效果相同且更灵活。

**为什么 split 始终算 hash**：hash 计算在 split 的同一遍数据流中完成，几乎零成本（hash 计算速度 ≥500MB/s，远超磁盘 I/O）。这让"清单里有 hash"成为不变属性——即使用 quick 模式切割，事后想校验时 `cutx verify` 始终可用。如果 split 不算 hash，quick 模式切割的文件将永远无法事后校验，这太激进。

**考虑过的替代方案**：
- 默认 verify 模式：被否决，因为与"简单工具"定位不符，且对有经验的用户增加不必要的等待。
- `--skip-verify` 参数（跳过校验）：被否决，因为名字暗示"跳过安全检查"，语义负面。`--mode` 正面描述用户意图（quick=快，verify=校验），更清晰。
- `--pre-verify`（先校验再合并，读两遍）：被否决，100GB 文件读两遍浪费 50% I/O 时间，收益极低（边写边校验发现损坏后立即删除输出文件，效果一致）。
